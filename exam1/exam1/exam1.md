# EXAM1：深空舰队环境数据分析系统 (Deep Space Telemetry Analyzer)

## 📖 背景
公元 2055 年，人类“深空探索舰队”在代号为 Kepler-452b 的异星表面部署了大量自动化探测车（Rovers），用于采集地表的温度（Temperature）、辐射（Radiation）和大气完整度（Atmosphere）数据。
然而，由于异星磁场的严重干扰，探测车传回的 CSV 遥测日志中充斥着大量的“**脏数据**”（缺失值、乱码、超出物理极限的异常值）。

**你的任务：**
作为舰队的首席软件工程师，你需要使用 Java 开发一套基于面向对象设计模式的**控制台应用程序 (CLI)**。该系统需加载原始数据，利用特定设计模式进行数据清洗、环境分析预警、危机指令下发，并最终导出安全的结构化数据。

---

## 🛠️ 一、 核心架构与业务规范

为了保证舰队系统的标准化，你的代码必须严格遵循以下具体的业务规则和架构约定：

### 1. 领域模型构建 (Factory Pattern)
*   **`TelemetryRecord` (遥测记录类)**：封装 CSV 数据行。属性需包含：时间戳、探测车ID、探测车类型、传感器类型、数值、状态。
*   **`Rover` (探测车抽象类/接口)**：包含基础属性和行为（如 `executeCommand()`）。
    *   必须通过 **工厂模式** 根据 CSV 中的 `RoverType` 字段，实例化为三个具体子类：`TrackedRover` (履带式)、`HoverRover` (悬浮式)、`WalkerRover` (步行式)。

### 2. 数据清洗规则 (Strategy Pattern)
必须设计一个 `DataCleaningStrategy` 接口，并实现以下**两种策略**供用户在控制台切换：

*   **策略 A：严格丢弃策略 (`DropInvalidStrategy`)**
    *   **规则**：遇到 `Value` 字段为空、无法解析为数字，或 `Status` 字段值为 `"ERROR"` 的记录，**直接整行丢弃**。
*   **策略 B：智能填充与修正策略 (`SmartFillStrategy`)**
    *   **规则 1 (修正非数字/为空)**：根据传感器类型填充安全默认值（Temperature 填 `-50.0`，Radiation 填 `100.0`，Atmosphere 填 `95.0`）。
    *   **规则 2 (修正越界值)**：数值若超出物理极限（温度 <-150或>150，辐射 <0或>5000，大气 <0或>100），同样使用上述安全默认值覆盖。
    *   **规则 3 (状态重置)**：修正后的记录，其 `Status` 字段强制修改为 `"REPAIRED"`。

### 3. 环境分析与预警联动 (Observer Pattern)
系统需具备一个 `DataAnalyzer`（数据分析器，**作为 Subject**），负责按时间顺序扫描有效数据。

*   **触发危机条件**：当发现**同一台探测车 (RoverID)** 连续 **2次** 传回的 `Radiation` 数值 **> 400.0** 时，触发“辐射风暴危机”。
*   **观察者联动 (Observers)**：危机触发时，自动通知以下三个独立的观察者：
    1.  `ConsoleAlertObserver`：在控制台打印高亮警告。
    2.  `LogFileObserver`：将告警信息追加写入本地 `alerts.log`。
    3.  `CommandCenterObserver`：通知指挥中心下发指令。

### 4. 危机指令下发 (Command Pattern)
指挥中心收到通知后，使用**命令模式**对涉事探测车下发指令：
*   **指令接口 (`RoverCommand`)** 包含 `execute()` 方法。
*   自动将以下两个命令放入该探测车的指令队列并执行：
    *   `ShieldCommand`：执行时打印 “探测车 {RoverID} 已开启电磁防护罩”。
    *   `MoveCommand`：执行时打印 “探测车 {RoverID} 正在向基地撤离”。

## 💻 二、 命令行交互界面 (CLI) 规范

系统的控制台入口（`Main` 类）必须实现一个持续运行的交互式循环（如 `while(true)`），直到用户选择退出。界面必须包含**状态栏**和**固定编号的菜单项**。

### 1. 主菜单UI标准
每次执行完一个指令返回主菜单时，必须打印如下格式的界面（**注意顶部状态栏必须动态更新**）：

```text
======================================================
      深空探测舰队 - 异星环境分析控制台 V1.0
======================================================
[ 数据状态: 已加载 8500 条 | 当前策略: 智能填充与修正策略 ]

  1. 加载原始数据并执行清洗 (Load & Clean)
  2. 切换数据清洗策略 (Change Strategy)
  3. 执行辐射风暴危机扫描 (Run Analysis)
  4. 查看探测车指令执行记录 (View Command Logs)
  5. 导出清洗后的结构化数据 (Export JSON)
  0. 退出系统 (Exit)
======================================================
请输入您的操作指令 (0-5): 
```
*(注：系统刚启动时，数据状态应显示“未加载数据”，当前策略默认显示“严格丢弃策略”。)*

### 2. 各选项执行逻辑与输出规范

**【选项 1：加载原始数据并执行清洗】**
*   **行为**：系统提示用户输入文件名（按回车默认读取 `raw_telemetry.csv`）。读取文件后，立刻应用**当前状态栏中显示的策略**进行数据清洗，并将清洗后的数据保存在内存中（如 `List<TelemetryRecord>`）。
*   **标准输出**：
    ```text
    > 正在读取并清洗数据...
    > 处理完成！
    > 原始数据总行数: 10000 行
    > 剔除/修复异常数据: 1500 行
    > 最终有效数据保留: 8500 行
    > 按任意键返回主菜单...
    ```

**【选项 2：切换数据清洗策略】**
*   **行为**：提供子菜单让用户选择策略。选择后，更新状态栏，但**不立即触发清洗**（需提示用户重新执行选项1才能生效）。
*   **标准输出**：
    ```text
    > 请选择新的清洗策略：
      A. 严格丢弃策略 (DropInvalidStrategy)
      B. 智能填充与修正策略 (SmartFillStrategy)
    > 请输入 A 或 B: B
    > 策略已切换为: 智能填充与修正策略。
    > (提示：请重新执行菜单 [1] 以应用新策略重新加载数据)
    > 按任意键返回主菜单...
    ```

**【选项 3：执行辐射风暴危机扫描】**
*   **防呆设计**：如果未执行过选项1，必须拦截并提示：“错误：内存中无有效数据，请先执行 [1] 加载数据！”。
*   **行为**：触发 `DataAnalyzer` 遍历内存中的有效数据。当满足触发条件（连续2次辐射>400）时，通过**观察者模式**触发告警，并在控制台实时打印 `ConsoleAlertObserver` 的输出。
*   **标准输出**（假设R-02和R-05触发了危机）：
    ```text
    > 正在进行全舰队环境数据扫描...
    [CRITICAL] 探测车 R-02 遭遇辐射风暴！(时间: 2055-10-12T08:01:22Z)
    [CRITICAL] 探测车 R-05 遭遇辐射风暴！(时间: 2055-10-12T08:05:10Z)
    > 扫描完毕。共发现 2 起极度危险事件，已记录至 alerts.log，并交由指挥中心处理。
    > 按任意键返回主菜单...
    ```

**【选项 4：查看探测车指令执行记录】**
*   **行为**：展示由**命令模式**执行的具体动作。当选项3扫描出危机并通知 `CommandCenterObserver` 后，指挥中心对涉事探测车下发的指令日志。
*   **标准输出**：
    ```text
    > === 舰队指令下发与执行记录 ===
    > [R-02] 接收指令: ShieldCommand... 执行成功: 探测车 R-02 已开启电磁防护罩。
    > [R-02] 接收指令: MoveCommand... 执行成功: 探测车 R-02 正在向基地撤离。
    > [R-05] 接收指令: ShieldCommand... 执行成功: 探测车 R-05 已开启电磁防护罩。
    > [R-05] 接收指令: MoveCommand... 执行成功: 探测车 R-05 正在向基地撤离。
    > === 记录结束 ===
    > 按任意键返回主菜单...
    ```

**【选项 5：导出清洗后的结构化数据】**
*   **防呆设计**：同选项3，无数据时需拦截。
*   **行为**：将内存中的有效数据利用第三方库序列化为 JSON。
*   **标准输出**：
    ```text
    > 正在生成 JSON 文件...
    > 导出成功！文件已保存至: ./clean_telemetry.json
    > 按任意键返回主菜单...
    ```

**【选项 0：退出系统】**
*   **行为**：终止循环，退出程序。
*   **标准输出**：
    ```text
    > 正在关闭指挥中心系统...
    > 通讯链路已断开，再见。
    ```

## 📄 三、 输出文件格式要求

程序在运行过程中生成的两个关键文件，必须严格符合以下格式，以便助教使用脚本进行自动化打分：

### 1. `clean_telemetry.json` (选项5导出)
必须是标准的 JSON 数组格式（严禁手动拼接字符串）。示例：
```json
[
  {
    "timestamp": "2055-10-12T08:00:00Z",
    "roverId": "R-01",
    "roverType": "Tracked",
    "sensorType": "Temperature",
    "value": -45.2,
    "status": "OK"
  },
  {
    "timestamp": "2055-10-12T08:00:05Z",
    "roverId": "R-02",
    "roverType": "Hover",
    "sensorType": "Radiation",
    "value": 100.0,
    "status": "REPAIRED" 
  }
]
```

### 2. `alerts.log` (观察者2自动生成)
纯文本文件，每次运行需追加（Append）而不是覆盖。每一行必须包含时间戳和涉事探测车ID。示例：
```text
[2055-10-12T08:01:22Z] ALARM: Rover R-02 encountered a radiation storm.
[2055-10-12T08:05:10Z] ALARM: Rover R-05 encountered a radiation storm.
```

## 🚀 四、 编译与执行说明

本项目由于需要引入第三方 JSON 处理库，推荐使用 **Maven** 进行项目管理。
请确保在项目根目录（包含 `pom.xml` 和 `raw_telemetry.csv` 的位置）可以使用以下标准命令编译和运行你的系统：

**1. 编译项目 (自动下载依赖)：**
```bash
mvn clean compile
```

**2. 运行主程序 (进入交互式 CLI)：**
```bash
mvn exec:java -Dexec.mainClass="com.yourpackage.Main" 
```
*(注意：请将 `com.yourpackage.Main` 替换为你实际的入口类全限定名)*
